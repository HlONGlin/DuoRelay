## 1. Executive Summary

**What**: A web panel deployable as one binary, driving sing-box and mihomo and unifying their protocol sets (28 product coverage items) in one management interface.

**Why it is feasible**: Both kernels expose a Clash API control plane and each supports capabilities the other lacks. A single kernel cannot cover the full set; comparable panels such as v2rayA have significant gaps in protocol coverage, testing, connection management, and traffic statistics.

**How**: Go backend + Vue 3 frontend + SQLite. Parse nodes into a unified intermediate representation (IR), generate sing-box JSON or mihomo YAML, and run each kernel as an independent process. Proceed in two steps: single-kernel switching first, then primary/secondary coexistence for seamless mixed use.

**Delivery and schedule**: 5 phases, 6 quality gates, 100 person-days, about 20 weeks; target V1.0 release window 2026-11-02 through 2027-03-21.

**Three largest risks**: tight schedule for one developer; UDP forwarding compatibility during dual-kernel coexistence; and the need for real nodes to accept all 28 protocol capabilities. P0 will validate or mitigate these risks early.

## 2. Background and Motivation

- v2rayA is the closest product in form (web GUI + global transparent proxy), but is tied to the Xray kernel. It imports 11 protocols (VMess, VLESS, Shadowsocks, Trojan, Hysteria2, TUIC, Juicity, AnyTLS, WireGuard, SOCKS5, and HTTP(S)); its documentation explicitly excludes ShadowsocksR. Mieru, Sudoku, ShadowQUIC, Naive, Tor, and others are absent. Its speed testing, connection management, and traffic statistics are also comparatively limited (see §7).
- A single kernel cannot provide full coverage. The initial review of official documentation found:
  - **sing-box v1.14.4**: mainly 16 native proxy outbounds, plus OpenVPN, OpenConnect, and Tailscale endpoint capabilities.
  - **mihomo v1.19.33**: shared proxy types plus MASQUE, OpenVPN, Tailscale, ShadowTLS, SSR, Mieru, Sudoku, ShadowQUIC, TrustTunnel, Rematch, EasyTier, and ZeroTier adapters.
- Together they cover **28 product capability items**. Some are endpoints or routing adapters, not same-level outbound protocols. Both provide a Clash API control plane, making unified management feasible; this is a project premise.
- The design borrows s-ui's practice of managing a small set of fixed fields and passing through the rest, so new kernel fields do not force an immediate panel release.

> Protocol counts and comparison statements here carry forward the v1.1 review. Kernel versions change quickly: P0-03 must re-check the locked versions and revise §4 if needed.

## 3. Goals, Non-Goals, and Success Metrics

### 3.1 Project Goals

1. **Protocol coverage**: import, generate configuration for, and establish a real connection with at least one node for all 28 outbound/capability items.
2. **Subscription and link compatibility**: parse mainstream Base64 / Clash YAML / sing-box JSON subscriptions and share links for the supported protocols.
3. **Web-panel delivery**: single-binary deployment and complete browser-based management; target local hosts, Docker, routers, and NAS devices.
4. **Dual-kernel cooperation**: make mixed use of kernel-specific nodes as transparent as possible, delivered in phases (§5.3).
5. **Feature and responsiveness advantage**: exceed v2rayA in testing, connections, traffic, rules, and diagnostics while meeting §7.3 budgets.

### 3.2 Non-Goals (Not in V1)

- Multi-user management and traffic billing (a server-panel concern).
- Native mobile apps (the web UI must still work fully in mobile browsers).
- Building a proxy kernel or protocol implementation from scratch.
- Global TUN transparent proxy on Windows/macOS (V1 targets Linux first).
- Selling/recommending nodes or providers, or providing account systems inside the panel.

## 5. Overall Architecture

### 5.1 Layered Structure

```text
┌──────────────────────────────────────────┐
│ Web frontend (Vue 3 + TS, embedded binary)│
└──────────────┬────────────────┬──────────┘
               │ REST           │ WebSocket (connections/traffic/logs/tasks/alerts)
┌──────────────▼────────────────▼──────────┐
│ Go panel backend                         │
│ auth/session; node/subscription/group DB  │
│ 28 parsers -> unified IR                  │
│ generators -> sing-box JSON / mihomo YAML │
│ validation/versioning/rollback            │
│ kernel process manager and Clash API      │
│ task queue and alert center               │
└──────────────┬────────────────┬──────────┘
               ▼                ▼
          sing-box process   mihomo process
```

### 5.2 Unified Node Model (IR)

- Parse all protocols into a unified intermediate structure split into **server / transport / security / protocol-specific fields**; each generator emits its target configuration.
- If a protocol belongs to one kernel only (§4.1), generate for that owner; do not attempt lossy cross-kernel conversion.
- Following s-ui's approach, manage a few fixed fields and pass unrecognized fields through `Extra` unchanged.

```go
type Node struct {
    ID, Name  string
    Protocol  string            // one of the 28 coverage items
    Owner     KernelSet         // sing-box, mihomo, or both
    Server    Server            // host, port
    Transport Transport         // tcp / ws / grpc / h2 / quic ...
    Security  Security          // none / tls / reality, including SNI, ALPN, fingerprint
    Proto     map[string]any    // protocol fields validated by schema
    Extra     map[string]any    // pass-through fields unknown to the panel
    Source    Source            // subscription ID or manual entry
}
```

### 5.3 Dual-Kernel Runtime Strategy (Two Phases)

- **Phase 1 (MVP): single-kernel switching.** Run one kernel at a time. Selecting a node starts its owning kernel; switching across kernels restarts it. This is simple and predictable and delivers coverage first.
- **Phase 2 (V1): primary/secondary coexistence.** sing-box is primary and owns TUN/global traffic; mihomo runs as secondary with a local mixed inbound. For each secondary-only node, the primary emits a SOCKS outbound pointing to the secondary inbound, allowing both kernels' protocols in one setup.
  - Risk: UDP protocols such as TUIC/Hysteria2 may not work through SOCKS5 UDP forwarding. If not feasible, those protocols fall back to "switch to the secondary kernel".
  - Validate early in **P0-08 (week 2)**. Its result determines whether P2 implements full chaining or degraded chaining, rather than discovering a blocker in week 10.
- **Secondary inbound security**: bind only to `127.0.0.1` on a random port and require username/password authentication.

### 5.4 Configuration Validation and Rollback

Before starting a kernel, always run `sing-box check` or `mihomo -t`. On failure, restore the previous working configuration, report the error in the panel, and avoid taking down connectivity.

1. Store every generated configuration as a version with validation result, trigger, and timestamp; retain the latest 50.
2. If the process exits or the Clash API is unreachable within 10 seconds of startup, automatically roll back and alert.
3. Let users inspect version differences and roll back to any version in the panel.

### 5.6 API Plan

**REST modules**: `/api/auth`, `/nodes`, `/subscriptions`, `/groups`, `/kernel` (status/start/stop/switch/upgrade), `/config` (versions/preview/rollback), `/speedtest`, `/rules`, `/rulesets`, `/dns`, `/connections`, `/traffic`, `/logs`, `/diagnose`, `/alerts`, `/settings`, `/system`.

### 5.8 Security Design (Deliver in P1)

| Area | Control |
|---|---|
| Default listener | Bind to `127.0.0.1`; require explicit configuration for external access; force administrator password setup on first run; no default password. |
| Kernel control plane | Bind Clash API to localhost or Unix socket; use a random secret; never expose publicly. |
| Sensitive data | Encrypt subscription URLs and node secrets with AES-GCM; master-key file mode 0600; redact logs and exports by default. |
| Login | Rate-limit and lock out login attempts; session cookies use HttpOnly + SameSite; protect mutations against CSRF. |
| Commands | Invoke kernels with argument arrays, never shell concatenation; never put user input into command strings. |
| Subscription fetch | Enforce timeouts and size limits; make private-network access configurable because LAN subscriptions can be legitimate. |
| Privileges | Prefer Linux capabilities for TUN over running the entire panel as root. |

## 7. Comparison and Experience Plan (Continues v1.1)

The goal is not only more protocols: features and UI responsiveness should also create a measurable gap versus v2rayA. Every item below is an acceptance point or hard metric, not a vague claim of a better experience.

### 7.1 Four Structural Gaps Identified in v2rayA

Based on a review of its official README, documentation, and GitHub issues at the time:
1. **Narrow protocol set**: 11 importable protocols; the project explicitly says it does not support ShadowsocksR. Mieru, Sudoku, ShadowQUIC, TrustTunnel, Naive, Tor, and OpenConnect are absent.
2. **Basic testing**: manual Ping and HTTP latency buttons, without latency sorting or automatic removal of dead nodes. GitHub issue #2077 (2026-10) was requesting those features.
3. **No connection/traffic views**: no live connection list or per-node/daily traffic statistics; troubleshooting relies on log inspection.
4. **Custom routing DSL**: RoutingA is capable, but users must learn a proprietary mini-language that does not interoperate with sing-box/mihomo rule-set ecosystems; multi-outbound routing requires handwritten rules.

> Re-check these comparison facts against official sources in P0-03 and again at P4-02.

### 7.2 Feature Comparison

| Dimension | v2rayA | DuoRelay |
|---|---|---|
| Protocols | 11, no SSR | 28 coverage items (§4) |
| Testing | Manual Ping / HTTP latency | One-click concurrent real latency + download test + jitter/loss, sorted by latency |
| Node selection | Lowest latency in group or fixed node | Scheduled tests, remove/switch failed nodes, filter by region/multiplier/tag |
| Connections | None | Live destination/rule/outbound-chain/rate list; disconnect individual connection |
| Traffic | None | Live rates, per-node/daily totals, subscription quota/expiry |
| Rules | RoutingA proprietary DSL | Native rule sets for both kernels, online updates, visual editor, and instant domain-to-rule hit tester |
| DNS | Basic settings | Multiple upstreams, routing, FakeIP toggle, one-click leak test |
| Diagnostics | Inspect logs | IP/location, DNS leak, IPv6, and routing checks with individual results and fixes |
| Stability | Manual handling after crash | Kernel restart, config history/rollback, panel alerts for update failure/all nodes down/crash |
| Bulk actions | Limited | Multi-select tests/delete/move, drag sorting, tags, favorites, global search |

### 7.3 UI Smoothness: Performance Budget

| Metric | Target |
|---|---|
| First usable view | <800ms on LAN; embedded frontend assets total <1.5MB compressed |
| Large lists | 10,000 virtualized nodes at ≥55fps; search/filter results within 100ms |
| Interaction | Click feedback <50ms with optimistic updates; same-kernel node switch <1s end-to-end |
| Live data | WebSocket for connections, traffic, logs; **no frontend polling**; incremental charts |
| Heavy tasks | 500-node concurrent test does not block UI; streamed, cancellable progress |
| Low-end device | Dashboard/list remain usable on a 512MB router using virtualization/pagination fallback |

Decide these architectural points in P1: aggregate dashboard API; cache kernel/Clash API data; run tests as asynchronous backend jobs; enable SQLite WAL and indexes for frequent queries.

### 7.4 UI/UX Principles

- **Dashboard as home**: runtime, outbound, live rates, connections, and today's traffic visible without navigating deeper.
- **Frequent actions inline**: switch, test, and update a subscription in at most two clicks from a list row.
- **Global Ctrl+K palette**: search nodes, navigate, and run actions from one place.
- **Four essentials for long operations**: progress, cancellation, background execution, and completion notice.
- **Human-readable errors**: state what happened, why, and provide a one-click fix; do not dump raw kernel errors on users.
- **Consistent across devices**: responsive mobile-browser management, dark mode, and real checks in major browsers. Avoid v2rayA's reported Safari blank-screen issue.

## 8. Technology Choices

| Layer | Choice | Reason |
|---|---|---|
| Backend | Go | Same language family as both kernels; consistent ecosystem/toolchain. |
| Frontend | Vue 3 + TypeScript | Embed build output in backend binary for single-file deployment. |
| Storage | SQLite | No external service; suitable for routers and NAS. |
| Kernel integration | Separate processes | Both kernels are GPLv3; process isolation avoids license coupling and allows independent upgrades. |
| Deployment | systemd / Docker | Two distribution paths. |

### 8.1 Candidate Libraries (Decide in P0-10 and Record in ADR)

| Use | Candidate | Trade-off |
|---|---|---|
| SQLite driver | Pure-Go driver such as `modernc.org/sqlite` | No CGO, simpler ARM/MIPS cross-compilation; slower than CGO but sufficient here. |
| HTTP router | chi or echo | Lightweight with complete middleware. |
| WebSocket | coder/websocket or gorilla/websocket | Choose one; evaluate backpressure and close semantics. |
| YAML | yaml.v3 | Generate mihomo config; retain readable key order. |
| Frontend UI | Naive UI or Element Plus, imported selectively | Must meet <1.5MB compressed bundle; measure. |
| Charts | uPlot (preferred) or selectively imported ECharts | Small bundle and incremental live rendering; uPlot is favored for size/frame rate. |
| Virtual scrolling | @tanstack/vue-virtual or vue-virtual-scroller | Benchmark 10,000 rows at ≥55fps before choosing. |
| Frontend state | Pinia | Standard for Vue 3. |
| E2E | Playwright | Chromium/Firefox/WebKit, including Safari compatibility checks. |

## 12. Build, Release, and Operations

### 12.1 Build/Release Pipeline

- **CI**: GitHub Actions: lint → tests → frontend build → backend build → validation → package.
- **Targets**: V1 Linux amd64/arm64 for VPS, NAS, ARM routers; armv7/mipsle deferred to V2.
- **Artifacts**: compressed single-binary package + checksum; multi-arch Docker image with kernels; installer and systemd unit.
- **Versioning**: semantic `major.minor.patch`; release notes grouped into Added / Changed / Fixed / Known limitations.

### 12.2 Kernel Version Management

- `kernels.lock` pins versions/checksums. Release packages do not bundle kernel binaries; first run/installer downloads and verifies them. Docker image bundles them.
- Upgrade: change lockfile → CI validates all golden configs on both kernels → connectivity matrix → manual smoke test → merge.
- Distributing kernel binaries, including Docker images, must meet GPLv3 obligations: preserve licenses and provide corresponding source access (P4-06).
